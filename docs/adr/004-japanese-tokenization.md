# ADR-004: 日本語の分割に bigram を使う

- ステータス: 採用
- 日付: 2026-10-29
- 関連: #8

## 背景

段階1 の索引語検索で、日本語のタイトル・著者名・内容紹介を索引語に分割する方式を決める。主な選択肢は、文字の bigram（2文字ずつ区切る）と、形態素解析（kuromoji / Sudachi など）の二つ。

検索対象の書籍データ（[ADR-002](002-data-source.md)）には次の特徴がある。

- タイトルや内容紹介に、固有名詞・新語・作品名が多い。これらは形態素解析の辞書に載っていないことが多い
- 著者名はさまざまな表記で書かれる

## 決定

**段階1 のベースラインでは、日本語の分割に bigram を使う。** 形態素解析との比較は、評価セットができた後に nDCG で行う。

### 決め手

1. **取りこぼしが少ない。** 辞書に依存しないので、未知語・新語・作品名でもヒットする。ベースラインは、まず再現率を確保したい
2. **辞書の保守が要らない。** ユーザー辞書を育てる作業が発生しない
3. **段階2 で弱点が補われる見込みがある。** bigram の弱点は精度（誤ヒット）だが、段階2 のハイブリッド検索では意味の近さをベクトル側が扱う。索引語側は再現率を担う役割に寄せられる

## 検討した選択肢

### 形態素解析（kuromoji / Sudachi）

| | bigram | 形態素解析 |
|---|---|---|
| 再現率 | 高い。辞書にない語でもヒットする | 辞書にない語や、区切り方が違う語を取りこぼす |
| 精度 | 誤ヒットがある（例: 「京都」で「東京都」がヒットする） | 高い |
| 1文字のクエリ | そのままではヒットしない（「愛」「海」など） | 1語として切り出されればヒットする |
| 索引サイズ | 大きい | 小さい |
| 運用 | 辞書の保守が要らない | ユーザー辞書の保守が要る |
| 導入 | ES 標準 | プラグインの導入が必要 |

- 不採用の理由: ベースラインの段階では、精度より取りこぼしの少なさを優先する。どちらが良いかは書籍データとクエリの性質に依存するため、評価セットで測ってから判断する

### bigram と形態素解析の併用（マルチフィールド）

- 長所: 同じ項目を両方の方式で索引し、検索時に両方のフィールドを引ける。再現率と精度を両立しやすい。
- 不採用の理由（現時点）: ベースラインとしては構成が複雑になる。bigram 単独のベースラインを先に測り、改善案の一つとして併用を試す。

## 結果

- 段階1 の索引は、bigram による分割で作る。Elasticsearch に標準で組み込まれている `ngram` tokenizer / `cjk_bigram` filter で実現できる
- kuromoji と比較する際は、`analysis-kuromoji` プラグインを導入したイメージを用意する（[ADR-003](003-search-engine.md)）。プラグインのバージョンは ES 本体と一致させる必要がある
- 1文字のクエリはそのままではヒットしない。評価セットに 1文字のクエリを含める場合は、その結果を把握したうえで扱う
- 評価セットができた後、「bigram 単独」と「bigram + kuromoji のマルチフィールド」を同じ評価セットで比べ、nDCG@10 の差を記録する

## 見直し条件

- 評価セットで「bigram + kuromoji のマルチフィールド」が bigram 単独を nDCG@10 で上回った場合は、併用に切り替える。採用の基準にする改善幅は、評価セットの規模が決まった時点で本 ADR に追記する
- 段階2 のハイブリッド検索で、索引語側の誤ヒットが nDCG を下げている原因だと分かった場合
- 誤ヒットや 1文字のクエリの取りこぼしが、評価セットの失敗事例の主な原因になっている場合
