# ADR-001: 実装言語に Python / FastAPI を採用する

- ステータス: 採用
- 日付: 2026-10-27
- 関連: #1

## 背景

書籍検索 API と検索フォーム UI を作る。索引語検索のベースラインから始め、ベクトル検索・ハイブリッド検索・生成検索へ段階的に進める。各段階の成果物は「動いたこと」ではなく、前段階からの nDCG の改善幅とする。

| 段階 | 内容 |
|---|---|
| 1 | 索引語検索のベースライン（ES + 検索API + 最小UI + nDCG の測定） |
| 2 | ベクトル検索 → ハイブリッド（dense_vector / kNN + RRF） |
| 3 | 生成検索（RAG） |
| 4 | 一般公開（時期未定） |

決定済み: 投入元 openBD（内容紹介つき 約10万件）／ エンジン Elasticsearch 9.5 ／ 日本語の切り方 bigram

### 言語に求める要件

| # | 要件 | 理由 |
|---|---|---|
| 1 | Elasticsearch の公式クライアントがある | 段階1〜3 はすべて ES を経由する |
| 2 | 埋め込みベクトルをアプリ側で生成できる | 制約①により、ES 側に推論を任せられない |
| 3 | 評価セットを流して nDCG を計算できる | 段階1 の完了条件であり、段階2 以降も毎回使う |
| 4 | 検索経路を単純に保てる | 段階ごとの改善を測るとき、構成の複雑さを持ち込みたくない |

### 制約（2026-10-26 調査）

1. **ES の無料版（Basic）では埋め込みを生成できない。** NLP モデルのデプロイと `text_embedding` の推論は Platinum 以上で使える機能のため、段階2 では埋め込みの生成をアプリ側で行う。
2. **参考書籍『ベクトル検索実践入門』のサンプルコードは Python で書かれている。** 構成は Sentence Transformers / PyTorch / Faiss で、ほかの言語では読み替えが必要になる。

### 埋め込みはクエリごとにも必要になる

埋め込みを生成するのは、投入バッチで本文をベクトル化するときだけではない。**検索のたびに、クエリもベクトル化する必要がある。** そのため API層を Python 以外の言語で書くと、検索経路そのものが二言語にまたがる。

```
ブラウザ → Go(API) → Python(埋め込み) → Go → ES → Go → ブラウザ
```

## 決定

**API・検索処理・投入バッチ・nDCG 評価を Python / FastAPI で実装し、最小UI は TypeScript で実装する。**

```
TS(UI) ──HTTP──> Python(API・検索・埋め込み) ──> ES
                 Python(投入バッチ・nDCG評価)
```

UI と API は HTTP で分かれているので、言語が二つあっても構成は単純なまま保てる。検索経路は Python の中で完結する。

### 決め手

1. **埋め込みの生成とクエリ処理を同じプロセスで扱える。** sentence-transformers をそのまま使えるので、別の推論サービスを立てる必要がない（要件2・4）。
2. **評価と検索を同じ言語で書ける。** nDCG の計算は数十行程度で書ける。検索ロジックを直接呼んで評価できるので、改善のたびに回しやすい（要件3）。
3. **参考書籍のサンプルをほぼそのまま使える。** 段階2 以降の実装で、読み替えのコストがかからない。

## 検討した選択肢

### Go

- 長所: 公式クライアント `go-elasticsearch` がある。シングルバイナリで配布しやすく、並行処理にも強い。
- 不採用の理由:
  - sentence-transformers に相当するライブラリが無い。そのため段階2 では埋め込みを Python の別プロセスに任せるか、ONNX Runtime を直接扱うことになり、検索経路が二言語構成になる
  - 参考書籍のサンプルをすべて読み替える必要がある
  - 評価スクリプトを Python で書く場合、検索ロジックを二重に実装するか、HTTP 越しに評価するかのどちらかになる

### TypeScript / Node

- 長所: 公式クライアントがある。UI と言語を一本化できる。
- 不採用の理由（API層として）:
  - 埋め込みの生成が transformers.js / ONNX Runtime 経由になり、使えるモデルやツールが Python より少ない
  - 参考書籍のサンプルの読み替えが必要になる
- UI層では採用する

## 結果

- 段階1〜3 は、検索経路が Python の中で完結する
- nDCG の評価スクリプトから検索ロジックを直接呼べる
- 参考書籍のサンプルをほぼそのまま使える
- UI（TypeScript）と API（Python）の間で、HTTP のインターフェースを定義して管理する必要がある

## 見直し条件

- 段階4（一般公開）で、性能や運用の要件から API層の置き換えを検討する場合。ただしその場合も、クエリごとの埋め込みの生成は残る。そのため「API層だけを差し替える」では済まず、埋め込みサービスを常駐させる構成への変更になることを前提にする
- ES のライセンス変更や外部の推論 API の利用などで、アプリ側で埋め込みを生成する必要がなくなった場合
