# 開発フロー

Issue の起票から PR のマージまでの手順。どの変更も同じ手順・同じ基準で実装とレビューを行う。

起票と実装は Claude Code のプロジェクトスキル（`/spec`・`/implement`）として定義している。手順の詳細はスキル側を正とする。

| 工程 | 担当 | 定義 |
|---|---|---|
| 起票 | `/spec` | [.claude/skills/spec/](../.claude/skills/spec/SKILL.md) |
| 実装 → PR | `/implement <Issue番号>` | [.claude/skills/implement/](../.claude/skills/implement/SKILL.md) |
| レビュー | `reviewer` サブエージェント（`/implement` から呼ぶ） | [.claude/agents/reviewer.md](../.claude/agents/reviewer.md) |
| マージ | 人 | GitHub 上で PR を読んでマージする |

## ブランチ

- `main` と短命の作業ブランチだけで運用する（GitHub Flow）
- 1 Issue = 1 ブランチ = 1 PR。Issue のない変更は作らない
- 作業ブランチ: `feature/issue#<番号>`。コマンドで指定するときはダブルクォートで囲む
- `main` への直接 push は禁止（フックと branch protection で止めている）

`develop` や `release/*` は置かない。公開中の版と開発中の版を分ける必要が出たときに見直す。

## Issue

Issue は設計書として扱う。設計判断は Issue で確定させ、実装中には判断しない。実装中に未決の判断が見つかったら、Issue を更新してから進む。

### 本文の構成

| 節 | 必須 | 中身 |
|---|---|---|
| 目的 | ○ | 何を、なぜやるか。範囲外と前提（依存する Issue） |
| 設計判断 | 判断があれば | 根拠（実測値は日付と条件つき）と、採らない案・その理由 |
| 評価 | ○ | 検索結果を変えるか。変える場合は測定方法と採用の基準。測らない場合はその理由 |
| やること | ○ | チェックボックス。おおむね1コミットの単位 |
| 完了条件 | ○ | 検証できる形（コマンド・件数・HTTP ステータスなど） |

- 決定済みの技術を覆す場合は、ADR の追加を やること に入れる
- 完了条件を独立に検証できる成果が2つ以上あれば、Issue を分ける
- 起票後に設計が変わったら、本文を直接更新し、変更点をコメントに残す

### 種類のラベル

1 Issue に1つ付ける。コミットと PR タイトルのプレフィックスはラベルから決まる。

| ラベル | 意味 | プレフィックス |
|---|---|---|
| `feature` | 機能追加 | `feat:` |
| `improvement` | 改修（既存機能の挙動や品質を変える。検索の精度改善を含む） | `feat:` / `perf:` |
| `bug` | 不具合修正 | `fix:` |
| `refactor` | 挙動を変えない構造の変更 | `refactor:` |
| `docs` | ドキュメント・ADR | `docs:` |
| `chore` | 環境・依存・設定・CI | `chore:` |

## 起票（`/spec`）

1. 目的・範囲外・前提を決める
2. 根拠が要る判断は、実測してから決める
3. 設計判断を1つずつ確認する
4. 下書きを全文で確認する
5. 起票し、種類のラベルを付ける

## 実装（`/implement`）

### 着手前

1. Issue を確認する。前提の Issue が閉じていない、ラベルがない、必須の節が欠けている場合は着手しない
2. Issue のままでは決められない判断がないか確認する。あれば Issue を更新してから進む
3. 実装計画（やること の順番と変えるファイル）の承認を取る

### 実装フェーズ（PR まで止まらない）

コードは [実装ルール](coding-rules.md) に沿って書く。書かれていないことは周囲のコードに合わせる。レビューの G1 も同じ基準で判定する。

4. `main` から作業ブランチを切る
5. やること を1項目ずつ実装し、項目ごとにコミットする
6. 完了条件を1つずつ検証する
7. 評価節で「検索結果を変える」とした場合は、`main` とブランチで nDCG を測る
8. `reviewer` サブエージェントがレビューする
9. PR を作る

次の場合は、止めずに **Draft PR** にする。冒頭に問題と Issue の更新案を書き、Issue を更新してから再開する。

- 設計の変更が必要になった
- 完了条件を満たせない
- 再レビューを2回しても必須の指摘が残る

## レビュー

実装の経緯を持たないサブエージェントに、Issue 本文・差分・完了条件の検証結果・評価結果だけを渡す（実装の経緯は渡さない）。経緯に引きずられずに「差分が Issue どおりか」を見るため。

| 観点 | 既定の重大度 |
|---|---|
| A. Issue との整合 | 必須 |
| B. 検索結果への影響 | 必須 |
| C. 正しさ | 必須 |
| D. 再現性 | 推奨 |
| E. 公開リポジトリ | 必須 |
| F. ドキュメントと ADR | 必須 |
| G. コードの書き方とテスト | 推奨 |

| 重大度 | 扱い |
|---|---|
| 必須 | 直してから PR にする。直したら再レビューする（2回まで） |
| 推奨 | 小さく直せるものは直す。直さないものは理由を PR に書く |
| 範囲外 | 直さない。別 Issue の候補として PR に書く |

各観点の項目は [reviewer.md](../.claude/agents/reviewer.md) を参照。

## コミット

- やること の1項目につき1コミット
- 1行目は `<プレフィックス>: <日本語の命令形>`（72文字以内）。本文には必要に応じて「なぜ」を書く
- レビュー指摘の修正は、元の項目と同じプレフィックスで別コミットにする

## マージ

- Merge commit のみ（squash・rebase はリポジトリ設定で無効にしている）。やること 単位のコミットを `main` の履歴に残すため
- マージ後のブランチは自動で削除される
