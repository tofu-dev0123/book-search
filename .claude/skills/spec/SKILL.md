book-search の Issue を起票する。Issue は設計書として扱う。設計判断はここで確定させ、実装（`/implement`）では判断しない。

フローの全体像は `docs/development-flow.md` を参照。

## 手順

### 1. 壁打ち

`$ARGUMENTS` をトピックのヒントにする（なければ何をしたいかを聞く）。次を決める。

- 目的: 何を、なぜやるか
- 範囲外: この Issue でやらないこと
- 前提: 先に閉じている必要がある Issue（`gh issue list --state all` で確認する）
- 種類のラベル（下表から1つ）

関連するコード・`docs/`・`docs/adr/` を読み、既存の決定と食い違わないか確認する。`CLAUDE.md` の「決定済みの技術」を覆す場合は、ADR の追加を やること に入れる。

### 2. 事前調査

根拠が要る判断は、推測で決めずに実測する（ローカルの ES・openBD の API・`_analyze` など）。

- 調査用のスクリプトや取得データは scratchpad に置き、リポジトリに入れない
- 実測値には日付と条件（件数・バージョンなど）を添える

### 3. 設計判断を1つずつ確認する

判断ごとに、案・根拠・トレードオフ・おすすめを示し、合意を取ってから次に進む。まとめて提示しない。

### 4. 下書きを全文で提示する

`${CLAUDE_SKILL_DIR}/template.md` の構成で本文を書き、scratchpad のファイルに保存して、タイトル・ラベルと一緒に提示する。

- タイトル: 何をするかが分かる日本語（例: `キーワード検索のエンドポイントを実装する`）。プレフィックスは付けない
- 必須の節: 目的・評価・やること・完了条件。設計判断は判断があるときだけ
- 評価節は「検索結果を変える」か「変えない」かを必ず明記する。`/implement` はこれで評価の要否を判定する
- やること は、おおむね1コミットの単位にする
- 完了条件は、コマンド・件数・HTTP ステータスなど検証できる形にする
- 完了条件を独立に検証できる成果が2つ以上あれば、Issue を分けることを提案する
- テンプレートのコメント `<!-- ... -->` は残さない

起票の前に、公開リポジトリとして問題がないか確認する。

- 書くのは技術的な判断と根拠だけ。個人的な事情や意向を書かない
- 秘密情報や、再配布できないデータ（openBD の取得データの全文など）を貼らない

修正を求められたら直して再提示する。

### 5. 起票する

承認を得てから実行する。

```bash
gh issue create --title "<タイトル>" --label <ラベル> --body-file <下書きのパス>
```

作成した Issue の URL を表示する。本文に署名やフッターは付けない。

## 種類のラベル

| ラベル | 意味 |
|---|---|
| `feature` | 機能追加 |
| `improvement` | 改修（既存機能の挙動や品質を変える。検索の精度改善を含む） |
| `bug` | 不具合修正 |
| `refactor` | 挙動を変えない構造の変更 |
| `docs` | ドキュメント・ADR |
| `chore` | 環境・依存・設定・CI |

## 起票後に設計が変わったとき

本文を直接更新し（`gh issue edit <番号> --body-file <パス>`）、変更点と理由をコメントに残す（`gh issue comment`）。本文が常に最新の設計になるようにする。
