# 機能追加フロー

次の機能について論点を決め、Issue にする。作るのは `/implement`（このスキルでは実装も設計書の変更もしない）。

> $ARGUMENTS

止まって確認するのは「2. 論点の報告」「3. モック」（画面が変わるときだけ）「4. Issue の分け方と下書き」の3か所。ほかに、内容から困りごとがつかめないとき（1）もそこで止まる。2 の壁打ちは、決まるまで何回繰り返してもよい。2 で足さないと決まったら終わる。それ以外は通しで進める。

## 守ること

- 要件や設計にない機能・設定項目を、決める前に足さない
- 決定済みの ADR は書き換えない。判断を変えるときは、新しい ADR を Issue に含める
- 報告・モック・Issue（件名を含む）に、シークレット・個人情報・実データを出さない。ダミーにする
- 料金・無料枠・ライブラリの使い方が論点になるときは、記憶に頼らず公式ドキュメントで確かめ、確認日を添える

## 1. 聞き取りと調査

1. 内容から、誰が・どこで・何をしたいのか（困りごと）をつかむ。足りなければ、ここで聞く
2. 関係する要件・設計書（場所は CLAUDE.md・README に従う）と今のコードを読み、今ある機能と制約を確かめる
3. 対象範囲と対象外、ほかの機能への影響を確かめる

## 2. 論点の報告（止まって確認）

次を示し、ユーザーの返事を待つ。

| 項目 | 内容 |
|---|---|
| 理解したこと | 困りごとと、足したい機能を数行で |
| 要件との関係 | 新しい機能か、既存の要件を変えるか。対象範囲と照らした意見（足さないほうがよいと考えるなら、そう言う） |
| 決めたいこと | 論点ごとに、選択肢・推奨・理由。今の設計・データの決まりにそろう案を推奨にする |
| 影響 | 変わる画面・API・データ・ほかの機能 |

- ユーザーの返事で論点が増えたり変わったりしたら、調べ直してもう一度示す
- 足さないと決まったら、そこで終わる

## 3. モック（画面が変わるときだけ。止まって確認）

論点が決まり、画面が変わるときは、決めるための試作のモックを作って見せ、ユーザーの返事を待つ。画面が変わらなければ飛ばす。

- 作り方（読み込む部品・見た目のそろえ方）は CLAUDE.md・rules に従う。決まりが無ければ、単体の HTML で作る
- 試作はリポジトリの外（作業用の一時ディレクトリ）に作り、使い捨てにする。正式なモックが要るなら、Issue の「やること」に入れる
- 状態（空・読み込み中・エラーなど）が要るなら、切り替えられるようにする
- 直しを頼まれたら直して見せ直す

## 4. Issue の分け方と下書き（止まって確認）

分け方と、各 Issue の下書きを示し、ユーザーの確認を待つ。

| 機能の大きさ | 分け方 |
|---|---|
| 1つの PR でレビューできる大きさに収まる | 実装の Issue を1つ。要件・設計書・モックの変更も、その Issue の「やること」に入れる（同じ PR で直す） |
| 2つ以上の PR にまたがる | 設計の Issue（要件・設計書・正式なモック・必要なら新しい ADR）を先にし、実装の Issue に分ける |

- `.github/ISSUE_TEMPLATE/implementation.md` の形で書く。「参照する設計書」「やること」「やらないこと」「完了条件」「依存」は、`/implement` が実装準備完了の判定で確かめるため必ず埋める
- 「参照する設計書」には読むべきパスを具体的に書く。無ければ「なし（この Issue が設計書）」
- 完了条件の手での確認は、起動方法（CLAUDE.md・README に従う）・操作・期待する結果まで具体的に書く。不要なら「なし」
- ラベルは `issue-driven.md` の表から1つ選ぶ（機能は `feature`、設計だけは `docs`）
- 「依存」に、先に終わっている必要がある Issue を書く。まだ番号がないものは、下書きでは「（下書きの何番目）」と書く
- 2・3 で決めたことと、決めなかったこと（やらないこと）を、そのまま Issue に書く

## 5. 起票

1. 下書きを一時ファイル（リポジトリの外）に書き、起票する

```bash
gh issue create --title "<件名>" --label <ラベル> --body-file <一時ファイル>
```

   - 複数を起票するときは、続けて出さず、依存の順に1分おきに裏で出す（GitHub の操作のペース）。1本のスクリプトで順に `gh issue create` し、出力された URL から番号を取り出して、次の下書きの「（下書きの何番目）」をその番号に置き換え、`sleep 60` してから次を出す。終わったら番号の一覧を伝える
2. Issue の URL と進める順番を伝え、「最初の Issue を `/implement <番号>` で進めますか？」と聞く
