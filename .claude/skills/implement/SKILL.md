# 実装フロー

Issue #$ARGUMENTS を実装する。止まって確認するのは「2. 計画」と「6. 手での確認」（手順があるときだけ）の2か所。ほかに、準備で「実装準備ができていない」と判定したときも止まる。それ以外は PR まで通しで進める。

`/implement` の実行は、コミット・push・PR の作成までの依頼を含む。PR のマージは人が行う。

## このリポジトリに要るもの

| もの | 使いみち | 無いとき |
|---|---|---|
| `.claude/rules/shared/branch-flow.md` | 作業ブランチを切る元・PR の宛先 | 止まって知らせる |
| `.claude/rules/shared/issue-driven.md` | ラベルとブランチ名・コミットの type の対応 | 止まって知らせる |
| `./scripts/check` | 検証（lint・型・テストなどをまとめたもの） | 止まって知らせる |
| `.claude/agents/reviewer.md` | レビュー | 止まって知らせる |
| `.claude/review.md` | リポジトリ固有のレビュー観点 | 無くてよい |

起動方法・設計書の場所・禁止事項は、CLAUDE.md・README に従う。

## 1. 準備

1. Issue とコメントを読む。コメントで設計が更新されていれば、本文より新しいものとして扱う

```bash
gh issue view $ARGUMENTS --json number,title,body,labels,state,comments
```

2. **実装準備完了の判定**：次をすべて確かめる。1つでも満たさなければ、ブランチを切る前に止まり、足りないものを一覧で知らせる（計画で補わない。Issue を直してから再実行してもらう）

| 確かめること | 確かめ方 |
|---|---|
| Issue が開いている | `state` |
| 種類のラベルがちょうど1つ付いている | `issue-driven.md` の表のラベル |
| 必須の節がそろっている | 参照する設計書・やること・やらないこと・完了条件・依存。`bug` なら再現手順・原因・影響範囲も |
| 依存の Issue がすべて閉じている | `gh issue view <番号> --json state` |

3. 「参照する設計書」を読む。「なし」なら、この Issue が設計書。ADR があるリポジトリでは、関係する ADR も読む
4. ブランチを切る。起点は `branch-flow.md` の「作業ブランチを切る元」、名前はラベルに対応するもの（`issue-driven.md`）。`#` を含むので名前はクォートする

```bash
git status --short                      # 未コミットの変更があれば止まって知らせる
git switch <起点>
git pull --ff-only origin <起点>
git switch -c "<プレフィックス>/issue#$ARGUMENTS"
```

5. `bug` なら、最新の起点でローカルに再現できることを確かめる（状態を変える操作が要るときは先に聞く）。再現しなければ（すでに直っているなど）止まって知らせる

## 2. 計画（止まって確認）

次を示し、ユーザーの確認を待つ。

| 項目 | 内容 |
|---|---|
| 理解したこと | Issue の目的と範囲を数行で |
| 作る・変えるファイル | 実装する順に |
| 書くテスト | 各テストで確かめること。`bug` なら直す前に落ちる（バグを再現する）テストを入れる。書けなければ、その理由 |
| 更新する設計書 | 実装に合わせて直すもの |
| 設計とのずれ | 設計書どおりに作れない点があれば、設計書の変更案（実装の前に決める） |
| 決めたいこと | 設計書・Issue から決められないことだけ。推奨案を添える |

- 「やらないこと」と、設計書にない機能・設定項目は計画に入れない
- **承認を得たら、PR まで止まらずに進む**（例外は「6. 手での確認」と「詰まったとき」）

## 3. 実装

- 計画どおりに実装する。計画から外れる必要が出たら「詰まったとき」に従う
- 設計書の更新も同じブランチで行う。ADR は書き換えず、判断を変えるなら新しい ADR を起こす
- 依存を足すときは、公式ドキュメントで最新の使い方を確かめる
- コミットは「やること」の区切りごとに作る。メッセージは `<type>: 日本語の要約`（type は `issue-driven.md`）。一時ファイル（リポジトリの外）に書いて `git commit -F` で渡す

## 4. 検証

- `./scripts/check` が通るまで直す
- `bug` なら、直す前にバグを再現するテストが落ち、直した後に通ることを確かめる
- 完了条件ごとに、満たしたことの根拠（テスト・コマンドの出力）を控える。レビューと PR で使う

## 5. レビュー

1. `reviewer` サブエージェントに次を渡してレビューを頼む。**実装の経緯や判断の理由は渡さない**（材料だけで判定させる）
   - Issue 本文（コメントによる更新を含む）
   - 起点との差分（`git diff <起点>...HEAD`）
   - `./scripts/check` の結果と、完了条件ごとの根拠
   - 2回目以降は、前回の指摘とその対応
2. 必須の指摘はすべて直す。推奨の指摘は直すか、直さない理由を PR の「注意事項・補足」に書く
3. 直したら `./scripts/check` を通し、もう一度レビューを頼む。再レビューを2回しても必須の指摘が残れば「詰まったとき」に従う

## 6. 手での確認

- 完了条件の手での確認が「なし」なら、確認を挟まずに 7 へ進む
- 手順があれば、次を示して止まり、ユーザーの確認を待つ
  - 自動で確かめたこと（`./scripts/check` の結果・レビューで直したこと）
  - 完了条件の手順（起動方法・操作・期待する結果）。`bug` なら再現手順をたどって起きないことも

## 7. PR

1. 未コミットの変更があればコミットする
2. push して、起点へ PR を作る。本文は一時ファイル（リポジトリの外）に書いて `--body-file` で渡す

```bash
git push -u origin "<ブランチ>"
gh pr create --base <起点> --title "<日本語の要約>" --body-file <一時ファイル>
```

PR の本文：

```markdown
## 概要
<何をしたか。Closes #$ARGUMENTS>

## 背景
<Issue の目的>

## 変更の詳細
<主な変更点>

## 動作確認
<完了条件ごとの根拠（テスト・コマンドの出力・手での確認）>

## 注意事項・補足
<直さなかった推奨の指摘とその理由など。無ければ「なし」>
```

3. CI があれば、終わるころに `gh pr checks` で結果を一度だけ確かめる（見張り続けない）。失敗したら直して push する
4. PR の URL と CI の結果を報告する

## 詰まったとき（Draft PR にして終える）

次のどれかに当たったら、止めずに Draft PR にして終える。

- 設計の変更が必要になった（Issue・設計書どおりでは実装できない）
- 完了条件を満たせない
- 再レビューを2回しても必須の指摘が残る

そこまでの変更をコミット・push し、`gh pr create --draft` で PR を作る。本文の「注意事項・補足」に、問題と Issue の更新案を書く。**Issue の本文は書き換えない**。

## マージの後

ユーザーから「マージした」と言われたら、起点を最新にし、作業ブランチをローカルとリモートから消す。Issue が閉じていることを確かめる。
