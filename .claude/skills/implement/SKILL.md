book-search の Issue `#$ARGUMENTS` を実装し、PR を作る。マージは人が行うので、このスキルは PR の作成で終わる。

フローの全体像は `docs/development-flow.md` を参照。Issue は設計書として扱う。設計判断は Issue で確定している前提で、実装中には判断しない。

## 着手前（問題があれば止まって確認を取る）

### 1. Issue を確認する

```bash
gh issue view <番号> --json number,title,body,labels,state,comments
```

次のいずれかに当たれば着手せず、理由を伝えて終える。

- Issue が閉じている
- 「前提」に書かれた Issue が閉じていない（`gh issue view <前提の番号> --json state`）
- 種類のラベル（`feature` / `improvement` / `bug` / `refactor` / `docs` / `chore`）が付いていない
- 必須の節（目的・評価・やること・完了条件）が欠けている
- 評価節が「検索結果を変える」か「変えない」かを明記していない

コメントで設計が更新されていることがあるので、コメントも読む。

### 2. 未決点を洗い出す

関連するコード・`docs/`・`docs/adr/` を読み、Issue のままでは決められない判断がないか確認する（仕様の抜け、既存コードや ADR との食い違い、採る案が書かれていない選択など）。

あれば止まって、判断ごとに案・根拠・おすすめを示す。合意が取れたら Issue を更新してから進む。

- 本文を更新する: `gh issue edit <番号> --body-file <パス>`
- 変更点と理由をコメントに残す: `gh issue comment <番号> --body "..."`

### 3. 実装計画の承認を取る

やること を実装順に並べ、各項目で変えるファイルを表で示す。Issue の順番と変える場合は理由を添える。

**承認を得たら、PR の作成まで止まらずに進む。**

## 実装フェーズ（PR まで止まらない）

ここから先は確認を取らない。次の場合は止めずに **Draft PR** にして終える（9 を参照）。

- 設計の変更が必要になった（Issue の設計判断どおりでは実装できない、採らない案が必要になった）
- 完了条件を満たせない
- 再レビューを2回しても必須の指摘が残る

Issue の本文は書き換えない。問題と Issue の更新案は Draft PR に書く。

### 4. ブランチを切る

```bash
git status --short        # 未コミットの変更があれば、その場で止めて伝える
git switch main
git pull --ff-only
git switch -c "feature/issue#<番号>"
```

- ブランチが既にあれば `git switch "feature/issue#<番号>"` で再開する。Issue のチェック済みの項目は飛ばす
- マージ済みのローカルの作業ブランチは削除する: `git branch --merged main` に出る `feature/issue#*` を `git branch -d` する

### 5. 実装とコミット

やること を1項目ずつ実装し、項目ごとにコミットする。

- Issue の範囲外の変更を入れない（ついでのリファクタ・整形など）。気付いたことは PR の「別 Issue の候補」に回す
- `docs/coding-rules.md` に沿う。書かれていないことは周囲のコードに合わせる
- 手順（起動・投入・設定など）が変わったら `docs/` を更新する

コミットメッセージ:

- 1行目: `<プレフィックス>: <日本語の命令形>`（72文字以内）。本文には必要に応じて「なぜ」を箇条書きで書く
- プレフィックスはラベルから決める（下表）
- `Co-Authored-By` などの署名は付けない

```bash
git add <ファイル>
git commit -m "$(cat <<'EOF'
<メッセージ>
EOF
)"
```

コミットしたら Issue の該当するチェックボックスを付ける（`gh issue view <番号> --json body -q .body` で本文を取り、`- [ ]` を `- [x]` にして `gh issue edit <番号> --body-file <パス>`）。

### 6. 完了条件を検証する

完了条件を1つずつ実際に確かめ、使ったコマンドと結果を控える（PR の「完了条件の検証」に使う）。

- 完了条件に書かれていなくても、次を必ず流して通す。結果も「完了条件の検証」に載せる

  ```bash
  uv run ruff format --check
  uv run ruff check
  uv run pytest
  ```

- 推測で「満たす」としない。確かめられなかった条件は「満たさない」とする

満たせない条件が残れば Draft PR にする。

### 7. 評価する

Issue の評価節が「検索結果を変える」なら `/measure` を呼び、`main` とブランチで nDCG を測る。結果を PR の「評価」に使う。

- 「変えない」なら飛ばす
- `/measure` がまだない、または評価セットがない場合は、完了条件を満たせないものとして Draft PR にする

### 8. レビューを受ける

`reviewer` サブエージェントを呼ぶ。実装の経緯は渡さず、次だけを渡す。

- Issue 本文（コメントで更新された設計があれば、それも）
- `git diff main...HEAD` の全文
- 6 の検証結果
- 7 の評価結果（あれば）

指摘の扱い:

| 重大度 | 扱い |
|---|---|
| 必須 | 直してコミットし、再レビューする。再レビューは2回まで。それでも残れば Draft PR にする |
| 推奨 | Issue の範囲内で小さく直せるものは直す。それ以外は直さない理由を PR に書く |
| 範囲外 | 直さない。PR の「別 Issue の候補」に書く |

- 指摘の修正は、元の項目と同じプレフィックスで別コミットにする
- 修正に設計の変更が要る場合は Draft PR にする
- 再レビューでは、前回の指摘とその対応も渡す

### 9. PR を作る

`${CLAUDE_SKILL_DIR}/pr-template.md` の構成で本文を書く。

- タイトル: `<プレフィックス>: <Issue のタイトル>`
- テンプレートのコメント `<!-- ... -->` は残さない。フッターや署名は付けない
- 公開リポジトリなので、技術的な判断と根拠だけを書く

```bash
git push -u origin "feature/issue#<番号>"
gh pr create --base main --title "<タイトル>" --body-file <本文のパス>
# Draft のとき: --draft を付け、本文の冒頭に「未解決」を置き、Closes ではなく Refs #<番号> にする
```

PR の URL を表示して終える。Draft にした場合は、止まった理由と次にやること（Issue の更新）を伝える。

## ラベルとプレフィックス

| ラベル | プレフィックス |
|---|---|
| `feature` | `feat:` |
| `improvement` | `feat:`（性能の改善は `perf:`） |
| `bug` | `fix:` |
| `refactor` | `refactor:` |
| `docs` | `docs:` |
| `chore` | `chore:` |
