# バグ調査フロー

次のバグを調べ、`bug` の Issue にする。直すのは `/implement`（このスキルでは直さない）。

> $ARGUMENTS

止まって確認するのは「2. 原因の報告」と「4. Issue の下書き」の2か所。ほかに、内容から情報が足りないとき（1）と、再現できないとき（2）もそこで止まる。それ以外は通しで進める。

## 守ること

- 状態を変える操作（データの登録・削除、外部への送信など）は、ローカルでも先に聞く
- 報告・Issue（件名を含む）に、シークレット・個人情報・実データを出さない。画面の写しやログに写っていても書き写さない。サンプルが要るときは、構造を保ったまま値をダミーにする
- 推測で原因を決めない。再現して確かめたこと、コードで確かめたことだけを書く

## 1. 再現・原因の調査

1. 内容から、起きている場所（画面・API・コマンドなど）・環境（ローカル / 検証 / 本番）と、期待する動きをつかむ。足りなければ、ここで聞く
2. 期待する動きを決めている設計書（場所は CLAUDE.md・README に従う）を読む
3. ローカルで再現する（起動方法は CLAUDE.md・README に従う）。手順と、そのとき見えたもの（画面・要求と応答・ログ・データの値）を残す
   - 検証・本番だけで起きるものは、ユーザーから受け取った様子をもとに、ローカルで同じ状態を作って再現する
4. 原因の場所（`ファイル:行`）と、なぜ起きるかを確かめる

## 2. 原因の報告（止まって確認）

次を示し、ユーザーの返事を待つ。

| 項目 | 内容 |
|---|---|
| 判定 | 不具合 / 仕様どおり / 両方（仕様どおりの動きと、別の不具合が重なっている。不具合の部分だけを 3 以降に進める） |
| 根拠 | 期待する動きを決めている設計書と、その箇所 |
| 再現 | 手順と、そのとき見えたもの |
| 原因 | `ファイル:行` と、なぜ起きるか |

- 仕様どおりなら、そこで終わる。仕様を変えたいと言われたら、`/feature` で扱う
- 再現できなければ起票しない。試したことと、足りない情報（手順・環境・様子）を伝えて止まる

## 3. 影響調査と直し方

ユーザーが原因を受け入れたら、次を調べる。

| 項目 | 調べること |
|---|---|
| 直し方 | どこをどう直すか。複数の案があれば推奨を添える |
| 影響範囲 | 直す所の呼び出し元・使っている箇所・データ（既存のデータを直す必要があるか） |
| 同じ種類の誤り | 原因と同じ書き方・同じ前提のコードを全体から検索する。見つかったものは同じ Issue で直すか、数が多ければ別の Issue にする |
| 書くテスト | 直す前に落ちるテスト。テストで再現できない所は、その理由と、手での確認で代えること |
| 設計書 | 直すと設計書とずれるか（ずれるなら、設計書の変更も Issue に入れる） |

## 4. Issue の下書き（止まって確認）

`.github/ISSUE_TEMPLATE/bug.md` の形で下書きを示し、ユーザーの確認を待つ。

- 1〜3 で確かめたことをそのまま書く。「参照する設計書」「やること」「やらないこと」「完了条件」「依存」は、`/implement` が実装準備完了の判定で確かめるため必ず埋める
- 完了条件には、再現手順をたどって起きないこと・直す前に落ちるテスト（書けなければ理由）・手での確認（起動方法・操作・期待する結果。不要なら「なし」）を入れる
- 1つの Issue は1つの PR でレビューできる大きさにする。大きければ分ける

## 5. 起票

1. 下書きを一時ファイル（リポジトリの外）に書き、起票する（件名にも実データを書かない）

```bash
gh issue create --title "<件名>" --label bug --body-file <一時ファイル>
```

   - 複数を起票するときは、続けて出さず、1分おきに裏で順に出す（GitHub の操作のペース）
2. Issue の URL を伝え、「続けて `/implement <番号>` で直しますか？」と聞く
