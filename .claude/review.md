# book-search 固有のレビュー観点

`reviewer` エージェントが汎用の観点（Issue との整合・conventions のルール）に加えて判定する。

判定の前に、差分に含まれる言語の実装ルールを Read する（R10 の基準）。`.py` を含むなら `docs/coding-rules.md`、`ui/` を含むなら `docs/coding-rules-ui.md`。

## 検索結果への影響（必須）

- R1. Issue の「評価」の節で「検索結果を変えない」とした差分に、クエリ・analyzer・マッピング・スコアリングなど検索結果を変えうる変更が入っていない
- R2. 検索結果を変える差分には、評価セットでの main との nDCG の前後比較が添えられている。Issue に「評価」の節がなくても、検索結果を変える差分なら必須とする
- R3. マッピングや analyzer を変える場合、index を作り直して再投入する手順が用意されている

## 正しさ（必須。Issue の仕様にない境界値の扱いは推奨）

- R4. 境界値と異常系が扱われている（0件・上限・空入力・不正な値・依存サービスの停止など）
- R5. 再実行しても結果が変わらない（投入・取得などの処理）
- R6. 例外を握りつぶしていない。エラー時の応答や終了コードが Issue の仕様と一致している

Issue の仕様にない境界値の扱いを推奨にするのは、実装側で仕様にない挙動を決めると Issue との整合（汎用の A3）とぶつかるため。仕様に足すべきだと判断した場合は、指摘にその旨を書く。

## 公開リポジトリ（必須）

- R7. 再配布できないデータ（openBD から取得したデータなど）がコミットされていない
- R8. コード・コメント・ドキュメント・コミットメッセージに、技術的な判断と根拠以外（個人的な事情や意向）が書かれていない

## ドキュメントと決定事項（必須）

- R9. 手順（起動・投入・設定など）の変更が `docs/` に反映されている。決定済みの技術（CLAUDE.md の「決定済みの技術」）を覆す変更であれば、ADR が追加されている

## コードの書き方（推奨）

- R10. 差分の言語の実装ルールに沿っている。Python は `docs/coding-rules.md`、UI は `docs/coding-rules-ui.md`。書かれていないことは周囲のコードに合っている。満たさない場合は、反しているルールの節（書かれていないことなら、比べた周囲のコード）も挙げる
- R11. 挙動を変える変更にはテストがある（テストの仕組みがない場合は、検証の手順が残っている）

## 再現性（推奨）

- R12. 乱数・外部データ・バージョンなど、結果を左右する条件が固定されているか、記録されている
- R13. 環境に依存する値（ホスト・ポート・パス・オリジンなど）がコードに直書きされず、設定で差し替えられる
